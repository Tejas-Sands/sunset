# Feasibility verdict

Build SUNSET's release-or-refund mechanism today, with a seeded original learning pack and a short working game. The existing design is coherent as a two-week prototype, but its eleven tasks include an escrow marketplace, content CMS, custom wallet authentication, storage authorization, release automation, offline distribution and a second service-payment system. This repository currently contains specifications, not an implemented product. Calling the entire existing scope a credible one-day deliverable would hide the integration and financial verification work.

The core NEAR utility is real: contributors escrow toward an immutable capped buyout; disclosure of the committed key credits the fixed creator; missed funding or disclosure deadlines make individual contributions refundable; the database cannot redirect those funds. Retain that utility and make it observable through actual contract receipts. A polished funding counter backed only by SQL would lose the point.

## Highest-risk findings

1. **Paid delivery before acceptance is a free-copy option.** CONTRACT.md lines 51–53 and 81 allow a buyer to receive the pack before accepting and subsequently obtain a full economic refund. They can also reserve the remaining funding capacity until expiry. This is disclosed honestly, but it undermines both paid-license economics and campaign liveness. For today's MVP, replace orders with immediate sponsorship contributions. Show a free sample before sponsorship; release the full pack after the cap. This removes orders, reservations, licensed delivery, school-license assignment, acceptance and order-expiry transitions together.
2. **A key commitment proves the submitted key, not that the key decrypts worthwhile content.** CONTRACT.md lines 83–85 correctly delegates key/ciphertext/plaintext correspondence to a reviewer. Seed and manually verify one exact original pack. Keep the reviewer attestation visible. Do not market this as trustless content quality or proof of rights.
3. **Rejected disclosure still discloses the key.** CONTRACT.md line 89 acknowledges this. The browser must check campaign state and key commitment locally before requesting a signature, never put keys in URLs, and never run an early test transaction against the real secret. A malicious authorized recipient can still disclose early. The mechanism cannot promise secrecy against recipients or fair exchange after every failure.
4. **Asynchronous withdrawals need their own state machine.** A returned transaction hash or successful initiating call does not prove transfer success. Debit credit into one pending operation before transfer; authenticate the callback by predecessor; match operation ID; restore only on confirmed transfer failure. Reserve callback gas and preallocate its state. If the callback fails, show pending uncertainty rather than offering another payout. NEAR documents independent receipts and the absence of automatic rollback of earlier receipts: https://docs.near.org/smart-contracts/anatomy/crosscontract .
5. **Preallocation must be physical.** `Option<[u8;32]>` grows when populated. Use a fixed 32-byte key field and a fixed state flag. Likewise, callback completion must not allocate a new record, grow a status string or create a previously missing beneficiary account. NEAR storage locks part of contract balance: https://docs.near.org/smart-contracts/anatomy/storage . All newly created identities and records need bounded funding for storage, separate from economic contributions.
6. **Offline export is a separate security boundary.** `JSON.stringify` inside a script tag does not by itself neutralize closing script tags. Encode pack data safely, render with textContent, and export the reviewed runtime with no remote fonts/images/scripts. Test the actual downloaded file in a fresh browser with networking disabled. A cached online page is weaker evidence.
7. **Zero-cost hosting is plausible, not already provisioned.** Real wallet capability, account access, deployment, free project quotas and actual upload permissions are integration gates. Do not replace them with fake successful provider adapters or present example accounts as deployed resources.

## Implementable reduction

Keep one Next.js application, one small original integer-maths game, one seeded encrypted data pack and one Rust testnet contract. A read-only catalog row or static checked-in manifest is enough metadata for day one; Supabase can hold catalog/storage if an actual free resource is available, but it must not own economic authority. An operator prepares the reviewed pack and immutable terms; a named reviewer approves its digest. Adults use a tested wallet for transactions. Learners need no wallet or cloud profile.

Contract surface: initialize; create immutable campaign; reviewer approve; contribute immediately; disclose committed key; claim expired contribution refund; withdraw credit; private withdrawal callback; bounded views. Contributions are capped atomically and excess is credited back. All amounts and timestamps use decimal strings in JSON. Creator, contributor and pending-operation balances are fixed records. Funding deadline equality and release deadline equality take the refund path. Releasing atomically empties escrow into the fixed creator credit. Refund and release are mutually exclusive.

Defer creator CRUD/upload UI, NEP-413 API sessions, managed key envelopes and signers, release-job leases, projection rebuilding, PWA service workers, separate access grants, AI, claims of classroom delivery and irreversible account locking. These each add independent failures. An independent reviewer can reveal from their saved local backup using their own wallet or direct documented CLI call. A real self-contained HTML download provides the offline proof. This remains a complete small product: play sample → inspect committed agreement → sponsor → reveal or refund → verify/play/export the funded pack.

This reduction intentionally changes prerelease paid licenses into sponsorship. Preserve that distinction in product copy rather than claiming the license marketplace has shipped. Separate finite service grants are a sensible next feature after the release/refund/withdrawal path is proven, not necessary for the core demonstration.

## Implementation priorities and acceptance

1. Pin the exact JSON ABI and pack envelope; create a shared non-secret SHA-256 key commitment vector. Build the game and safe standalone export independently while the contract is implemented.
2. Implement contract arithmetic and transitions first. Tests must exercise cap surplus, both deadline refund reasons, wrong reviewer/digest/key, duplicate reveal/refund, beneficiary immutability, and release/refund exclusivity.
3. Test withdrawal success, confirmed failure, wrong predecessor, stale/duplicate callback, low gas and callback failure. Assert total attached deposits equal storage retained plus escrow, credits, pending withdrawals and successful withdrawals. Unsolicited transfers remain surplus.
4. Compile a real Wasm artifact; native model tests alone do not prove host ABI behavior or NEAR receipt execution. Run Sandbox if available and record any missing runtime proof explicitly.
5. Connect the real wallet and RPC, verify finalized receipt outcomes and reread canonical state after mutation. Never submit another deposit automatically when the first outcome is unknown. Disable economic actions on network or code-identity disagreement.
6. Show one successful release and creator withdrawal, one underfunded refund, one funded-but-not-revealed refund, an independent disclosure without the application backend, and an exported game opened with all networking disabled. Record actual IDs and outcomes.

Do not remove deployment keys merely to make an immutability claim today. Mark the testnet deployment upgradeable until its exact source, binary, absence of upgrade/key-restoration routes and explicit signing decision have been checked. NEAR's key restrictions and locked-account caveats are documented at https://docs.near.org/protocol/accounts-contracts/access-keys .

The result is feasible as a focused hackathon MVP. The full prewritten CMS/marketplace/grants design should remain a roadmap, with no claim that its unopened checkboxes have been implemented or verified.
