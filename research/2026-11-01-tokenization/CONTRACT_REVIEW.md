**Findings.**

1. **P2 — qualify onward-transfer protection when a receiver reacquires the token.** `src/nft.rs:278` checks the current owner's account against the callback's receiver. If creator A starts `nft_transfer_call` to B, B transfers to C, C transfers back to B, and B's old callback then rejects, the resolver returns the token from B to A and resets B's newly chosen mirror. An additional compiled-Wasm reproduction confirmed that exact sequence. This matches the official reference resolver; it does not preserve all subsequent acquisitions by the same receiver account. The contract README's original statement that an onward transfer always preserves a later owner, and the design's absolute mirror-preservation wording, were too broad. Describe protection as applying when the current owner differs from that callback's receiver, and disclose the reacquisition case. Changing this behavior would require a separate semantics decision and tests, rather than an unreviewed callback nonce patch. **Resolved:** the implementer corrected the README and added a dedicated round-trip regression; the revised 9-scenario Wasm suite passed independently. The coordinating agent applied the same current-owner comparison and explicit reacquisition caveat to the design; independently reread and confirmed.

2. **P2 — reconcile the design with the selected no-lock behavior.** The design at review time still required an exact pending operation, settled-holder-only mirror updates and pending-mirror denial tests. The implementation intentionally has no NFT pending record, authenticates self callbacks and one ready result, and allows the provisional receiver to update its mirror. Rejection resets the mirror; acceptance preserves it. The contract README already describes this accurately. Update the design and verification checklist to reflect the engineering ruling, so future work does not restore a permanent liveness lock or claim checks that do not exist. **Disposition:** the coordinating agent corrected those three design requirements during review; independently reread and confirmed.

Both resolved findings concern the accuracy of the documented guarantee. Neither demonstrates external unauthorized transfer or diversion of escrow. No unresolved contract-review finding remains in this snapshot.

**Security and behavior assessed.**

- Ownership checks use the actual predecessor and current stored owner; no approval ID grants authority. Transfers reject invalid receivers and self-transfer. Token existence follows public release, with one mint event and no mint on repeated publication.
- The final minimal hardening also rejects a campaign whose reviewer account equals the creator predecessor, before registration or storage charging. Independently checked the guard, immutable creator assignment, unchanged-state native regression and compiled-Wasm rejection/valid-reviewer regression. The README accurately states that distinct account IDs cannot prove different human controllers or prevent collusion. This guard does not establish artifact quality or independent human review.
- Both transfer methods and `set_mirror` require exactly one yoctoNEAR. That deposit increments `security_deposits` without registering an account or altering escrow, creator credit, contributor records, storage collateral or withdrawal totals. The accounting identity includes that reserve on both sides and mutations are checked before persistence. The reserve is retained, not withdrawable sponsor credit.
- Owner and mirror fields use fixed-capacity arrays. Release, maximum owner length, a 512-byte mirror, transfers and resolver returns do not increase serialized state. The native maximum-record test covers five campaigns and 100 accounts with maximum-length account IDs; token recipients consume no financial participant slot.
- Resolver entry requires the contract predecessor, one result, zero attached deposit and a ready host result. Successful execution status is kept separate from receiver data. Canonical JSON `false` accepts; rejection, failure, malformed data and oversized data request return. A missing/not-ready callback panics without speculative ownership correction. Return resets the mirror through the same ownership helper used for ordinary transfer.
- The host reads at most five successful result bytes into Wasm, even for a 100 KB receiver result. That bounded policy agrees with the current reference implementation. It intentionally treats a longer encoding, including whitespace-padded `false`, as a request to return.
- Raw ABI scheduling targets the receiver's `nft_on_transfer`, passes sender/previous owner/token/message, attaches zero deposit and chains a private self resolver. It returns the resolver promise. There is a fresh remaining-gas check before scheduling, 15 Tgas allocated to the resolver and a scheduling margin. A scheduling panic is within the initiating receipt and should roll back that receipt's state; the host tests check transactional rollback, not actual protocol gas behavior.
- Existing compiled-Wasm scenarios cover accepted, rejected, failed, malformed, oversized and nested receiver outcomes, plus the round-trip acquisition limitation. A different onward owner and its mirror survive an earlier resolver; nested returns reset the mirror each time. A failed resolver itself leaves earlier ownership intact and creates no permanent pending lock. No automatic timeout recovery is claimed.
- Core methods accept omitted/null optional fields. Metadata has the standard collection fields, numeric millisecond timestamps and base64 manifest reference hash. Enumeration uses decimal-string supplies/indices, optional/null defaults, positive numeric limits and an upper bound of five existing campaigns. Mint, transfer and metadata changes use `EVENT_JSON`, `nep171` and version `1.2.0` with appropriate array data.
- Transfers and mirror updates leave the immutable manifest reference, committed hashes, released key, agreement, creator beneficiary and refund conditions intact. Public key and campaign views remain publicly readable; NFT ownership adds discovery-mirror authority without restricting public use or recovery. A mirror URI records a location, not availability or authenticity.
