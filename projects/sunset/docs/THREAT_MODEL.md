# SUNSET prototype threat model

## Assets and authority

The assets are contributed funds, the fixed beneficiary and agreement, the retained release key, committed resource bytes, independently usable copies and the current steward's maintenance authority. The local application illustrates their lifecycle. Its role selector and browser storage provide no authentication or adversarial financial protection. A deployed NEAR contract would be the financial and ownership authority; no live deployment or real receipt run is established here.

The intended actors are an adult creator, independent reviewer, adult sponsors, any valid release-key holder, a resource steward and learners who use public copies without an account or wallet. Adversaries include dishonest creators/reviewers, sponsors using many accounts, a compromised website, an unavailable or malicious mirror, leaked backups and a deployment-account controller.

## Boundaries and residual risks

| Boundary | Protection in the implementation | What remains trusted or unproven |
| --- | --- | --- |
| Uploaded pack → runtime | Strict fields, bounded plain-text data, distinct integer choices and a 5-MiB plaintext limit; uploaded code is not the game runtime. The standalone game embeds data safely and blocks network resources with its policy. | A schema-valid answer can still be wrong, offensive or ineffective. The runtime and browser must be trustworthy. Actual offline/mobile/accessibility execution remains unverified here. |
| Creator → reviewer | Review checks exact ciphertext, plaintext, manifest and key commitments, then exposes the decrypted questions and binds approval to the agreement. | The reviewer must inspect the content and rights honestly. Cryptographic equality does not establish authorship, licensing rights, educational merit or artifact availability. Colluding or mistaken adults can approve bad content. |
| Private backup → public release | AES-GCM authenticates encrypted content; domain-separated key and exact-byte hashes bind the retained material. Independent recovery rechecks commitments before writing a game. | Any key holder can disclose early. Demo keys are stored with browser data; this is not production secret custody. A secret submitted to a blockchain transaction is exposed even on rejection. Losing every matching backup can prevent timely release. |
| Browser rehearsal → financial authority | Visible simulated labels, exact decimal arithmetic, capped contributions, exclusive deadlines, replay checks and conservation tests. | Browser-local data and role names can be edited by the visitor or a compromised script. They are not wallet identities or balances. Local withdrawals have no pending receipts, fees or native transfer outcome. |
| Live read → configured contract | The viewer checks testnet chain identity, reviewed code hash and block identity before accepting views. Plans are unsigned. | RPC availability and integrity still matter; a correct hash does not prove code correctness. No live signing, deployed code identity or independent transaction receipt is verified by this prototype's local tests. |
| Contributor → escrow | The compiled contract implements fixed-owner campaign creation, exact deposits, capped funding, fixed beneficiary, time-based refund eligibility and pull withdrawals. Integer/state tests cover conservation. | Protocol Wasm compatibility, instrumented gas, actual balances and receipt execution need Sandbox. A direct native transfer to the account is unallocated surplus, not a campaign contribution. Original code/state storage collateral must be funded separately. |
| Withdrawal → asynchronous receipt | Contract operations bind the private callback to the account and operation ID. Only a confirmed failed transfer restores credit; duplicate/stale callbacks cannot pay again. | A failed or missing callback can leave a visible pending operation. Time passing is not proof of transfer failure; no timeout recredit is safe. Maximum-state callback gas and real failure behavior remain protocol verification gates. |
| Public caller → bounded storage | Owner-curated campaign creation, fixed campaign/account ceilings, bounded serialized state and storage allowances limit growth. | Public contributors can consume finite participant slots using valid deposits. This is a disclosed availability ceiling, not Sybil resistance or production capacity. No cleanup guarantee is claimed. |
| Steward → mirror metadata | Local stewardship mints once on release, permits only the current owner to transfer/update, resets a mirror on transfer and records history. Tests preserve the key, content commitments, beneficiary and money across transfer. | The owner can withhold a useful mirror or choose a misleading/unavailable host. The token is a maintenance right, not copyright, exclusive access, investment yield or a power to revoke offline copies. Local role checks remain rehearsal checks. |
| Mirror transport → retained resource | Exact manifest and ciphertext commitments plus the public key determine the resource. The mirror helper validates bounded HTTPS locations, verifies bytes and fails closed on altered content; controlled `Response` tests exercise the crypto path. | A URL setter cannot prove hosting, CORS behavior, DNS destination, uptime or successful delivery. Controlled fetch responses are not live network evidence. Keep independent copies; do not execute supplied remote code or trust a new manifest merely because a steward set its URL. |
| Deterministic policy → wallet | The coordination lab enforces separate simulated limits and emits explicit unsigned, testnet-pinned plans. | Browser policies do not restrict an independently controlled signer. There is no autonomous onchain spending authority, confidential inference or production agent security boundary. |
| Access budget → service claim | Local grants fix the provider/approver, cap spending, reject duplicate claims and refund expired remainder. | The approver must judge the actual service/evidence. These grant operations remain separate local logic; they are not part of the current core financial contract unless a later verified artifact explicitly implements them. |
| Deployment account → deployed code | Source and artifact hashes make the reviewed build identifiable. | Full-access keys retain upgrade/transfer authority even if the contract has no upgrade method. No immutable deployment is claimed. Key removal or mainnet use requires a separate reviewed decision and verified recovery/runtime evidence. |

## Stewardship integration record

The local APIs are [stewardship.mjs](../src/lib/stewardship.mjs), and the complete local journey is [verify-local.mjs](../scripts/verify-local.mjs). The token fixes maintenance responsibility after public release; it cannot change the released agreement or payout path. A transfer resets the selected mirror, so the receiving steward must verify and select its own mirror.

When the final contract/UI integration is frozen, update the ABI reference, callable export list and artifact hash in the maintained verification evidence, and verify ownership/callback behavior against that exact artifact. Standard compliance and live ownership must follow the actual implemented methods and executed receipt scenarios. Local ownership tests alone do not prove a deployed token, safe receiver contract behavior, marketplace interoperability or actual content retrieval.

## Recovery assumptions

Keep at least one independent copy of the encrypted artifact, exact manifest, committed identity and matching release backup before funding completes. After release, retain the public key and standalone game. An offline copy remains usable when the website or a steward disappears, provided the file and browser remain available. It cannot be revoked by later ownership transfer.

For live financial recovery, use the actual contract ABI with the adult's own signer and verify canonical state plus receipt outcomes. Stop when a withdrawal is pending or its transfer outcome is uncertain; record its operation and receipt chain rather than issuing a guessed replacement payment. Never post a private backup or secret release arguments publicly before intended release.

## Evidence and deployment limits

`node scripts/verify-local.mjs` checks real local cross-module transitions and retained-file recovery without sockets. `npm test` covers crypto, ledger, policy, transport-response and recovery boundaries. Compiled-Wasm tests run the binary against host doubles. These establish different layers and none substitutes for browser execution, NEAR Sandbox gas/balances/receipts, a reviewed testnet deployment, actual educator review or sponsor feedback.

See [the browser/protocol gap assessment](../../../research/2026-11-01-tokenization/VERIFICATION_GAPS.md), [contract review](../../../research/2026-11-01-council/contract-review.md) and [contract ABI/recovery documentation](../contracts/sunset/README.md). No mainnet suitability, immutability, confidential key service or measured learning outcome is claimed.
